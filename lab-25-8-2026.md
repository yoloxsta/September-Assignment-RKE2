## RKE2 Installation

### Step 1: Download and Install RKE2

```bash
# Update system
sudo apt update && sudo apt upgrade -y

# Install required packages
sudo apt install -y curl wget

# Download RKE2 installation script
curl -sfL https://get.rke2.io | sh -

# Check installed version
rpm -qa | grep rke2
# Output: rke2-server-1.35.7+rke2r1
```

### Step 2: Configure RKE2 Server

```bash
# Create configuration directory
sudo mkdir -p /etc/rancher/rke2

# Create RKE2 configuration file
sudo tee /etc/rancher/rke2/config.yaml <<EOF
server: https://13.58.33.90:9345
token: K10380502b48d9a9e5c8dd2771bec0a73a453734871c2552d4160a7d70ef8002615::server:8b85c84f01237500206346bd62777e03
tls-san:
  - 13.58.33.90
  - rke2-master-1
  - localhost
disable:
  - rke2-ingress-nginx  # We'll install it manually later
EOF
```

### Step 3: Enable and Start RKE2

```bash
# Enable RKE2 server service
sudo systemctl enable rke2-server

# Start RKE2 server
sudo systemctl start rke2-server

# Check status
sudo systemctl status rke2-server
```

### Step 4: Configure kubectl

```bash
# Create .kube directory
mkdir -p ~/.kube

# Copy kubeconfig
sudo cp /etc/rancher/rke2/kubeconfig.yaml ~/.kube/config

# Change ownership
sudo chown $USER:$USER ~/.kube/config

# Set environment variable
export KUBECONFIG=~/.kube/config

# Add to bashrc for persistence
echo 'export KUBECONFIG=~/.kube/config' >> ~/.bashrc

# Verify cluster access
kubectl get nodes
```

### Step 5: Verify Cluster

```bash
# Create test PVC

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: test-pvc
  namespace: default
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: local-path
  resources:

      storage: 1Gi

# Create test pod to use the PVC
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: test-storage
  namespace: default
spec:
  containers:
  - name: nginx
    image: nginx:latest
    volumeMounts:
    - name: data
      mountPath: /usr/share/nginx/html
  volumes:
  - name: data
    persistentVolumeClaim:
      claimName: test-pvc
EOF

# Verify pod is running
kubectl get pod test-storage

# Write data to PVC
kubectl exec test-storage -- sh -c "echo 'Hello from PVC' > /usr/share/nginx/html/index.html"

# Read data back
kubectl exec test-storage -- cat /usr/share/nginx/html/index.html

# Clean up test resources
kubectl delete pod test-storage
kubectl delete pvc test-pvc
```

### Step 2: Create NodePort Service for Ingress

```bash
# Create NodePort service to expose ingress controller
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Service
metadata:
  name: ingress-nginx-controller
  namespace: kube-system
spec:
  type: NodePort
  selector:
    app.kubernetes.io/component: controller
  ports:
  - name: http
    port: 80
    targetPort: 80
    nodePort: 30080
    protocol: TCP
  - name: https
    port: 443
    targetPort: 443
    nodePort: 30443
    protocol: TCP
EOF

# Verify service
kubectl get svc ingress-nginx-controller -n kube-system

# Output:
# NAME                       TYPE       CLUSTER-IP     EXTERNAL-IP   PORT(S)                      AGE
# ingress-nginx-controller   NodePort   10.43.75.137   <none>        80:30080/TCP,443:30443/TCP   7s
```

### Step 3: Create Ingress Resource

```bash
# Create ingress for demo application
cat <<EOF | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: demo-ingress
  namespace: demo-app
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  ingressClassName: nginx
  rules:
  - http:
      paths:
      - path: /demo
        pathType: Prefix
        backend:
          service:
            name: frontend
            port:
              number: 80
EOF

# Verify ingress
kubectl get ingress -n demo-app

# Describe ingress
kubectl describe ingress demo-ingress -n demo-app

# Output:
# Name:             demo-ingress
# Labels:           <none>
# Namespace:        demo-app
# Address:          172.31.0.169
# Ingress Class:    nginx
# Rules:
#   Host        Path  Backends
#   ----        ----  --------

#               /demo   frontend:80 (10.42.0.15:80,10.42.0.16:80)
```

## Production Ingress - HostNetwork Method

### Understanding Production Requirements

In production environments, you typically don't use NodePort because:
1. Non-standard ports (30080, 30443) are not user-friendly
2. Requires opening many high ports in firewalls
3. Not ideal for production traffic

**Production alternatives without cloud LoadBalancer:**
1. **HostNetwork** - Ingress binds directly to port 80/443 on node
2. **MetalLB** - Provides LoadBalancer-type services on bare metal
3. **External Load Balancer** - HAProxy/Nginx in front of cluster

### Step 1: Switch to HostNetwork

```bash
# Check current ingress controller configuration
kubectl get all -n kube-system | grep ingress

# Output:
# pod/helm-install-rke2-ingress-nginx-2kl9l                   0/1     Completed   0          47m
# pod/rke2-ingress-nginx-controller-x6s9f                     1/1     Running     0          46m
# service/ingress-nginx-controller                  NodePort    10.43.75.137    <none>        80:30080/TCP,443:30443/TCP   14m
# service/rke2-ingress-nginx-controller-admission   ClusterIP   10.43.179.20    <none>        443/TCP                      46m
# daemonset.apps/rke2-ingress-nginx-controller   1         1         1       1            1           kubernetes.io/os=linux   46m

# Note: It's a DaemonSet, not a Deployment!
```

### Step 2: Patch DaemonSet for HostNetwork

```bash
# Patch the DaemonSet to use hostNetwork
kubectl patch daemonset rke2-ingress-nginx-controller -n kube-system --type='json' -p='[
  {
    "op": "add",
    "path": "/spec/template/spec/hostNetwork",
    "value": true
  }
]'

# Output:
# daemonset.apps/rke2-ingress-nginx-controller patched

# Watch the pod restart
kubectl get pods -n kube-system -l app.kubernetes.io/component=controller -w

# Output:
# NAME                                  READY   STATUS    RESTARTS   AGE
# rke2-ingress-nginx-controller-bvsdx   0/1     Running   0          7s
# rke2-ingress-nginx-controller-bvsdx   1/1     Running   0          24s

# Press Ctrl+C when pod is Running 1/1
```

### Step 3: Verify HostNetwork

```bash

kubectl get pod -n kube-system -l app.kubernetes.io/component=controller -o yaml | grep -A2 hostNetwork

# Output:
```

### Troubleshooting: AWS Security Group

If the worker can't connect to the master, check security group rules:

**Required ports on master node:**
- **9345** - RKE2 server (required for agent registration)
- **6443** - Kubernetes API server
- **2379-2380** - etcd (for multi-master)

**Quick fix - allow all traffic between instances:**

```bash
# Option 1: Use same security group for both instances
# Add rule: All TCP from security group itself

# Option 2: Allow specific ports from worker IP
aws ec2 authorize-security-group-ingress \
  --group-id <master-sg-id> \
  --protocol tcp \
  --port 9345 \
  --cidr 172.31.10.92/32
```

### Issues Encountered

#### Issue 1: Insufficient Disk Space

**Symptom:**
```
Disk default-disk has 2.7GB available, but requires reserved 4GB
```

**Cause:**
- t2.medium instances have 8GB root volumes (default for Ubuntu AMI)
- Longhorn requires minimum 30% disk space reserved
- System and RKE2 already using ~5GB

**Solution Attempted:**
- Patched `storage-minimal-available-percentage` to 10%
- Patched `storage-over-provisioning-percentage` to 200%

**Result:** Partially resolved, but still not enough space for optimal operation

#### Issue 2: DNS Resolution Failures

**Symptom:**
```
curl: (6) Could not resolve host: longhorn-conversion-webhook.longhorn-system.svc
nslookup: can't resolve 'kubernetes.default'
```

**Cause:**
- CoreDNS service in RKE2 uses non-standard name (`rke2-coredns-rke2-coredns`)
- Intermittent DNS resolution across pods
- Network policy or CNI issues

**Solution Attempted:**
- Restarted CoreDNS deployment
- Created `kube-dns` service alias
- Tested DNS resolution with busybox pods

**Result:** DNS works intermittently, but not reliable enough for Longhorn

#### Issue 3: longhorn-manager Pod CrashLoopBackOff

**Symptom:**
```
longhorn-manager-nnh9n   1/2     CrashLoopBackOff   5 (77s ago)
```

**Logs:**
```
level=warning msg="Failed to check endpoint https://longhorn-conversion-webhook.longhorn-system.svc:9501/v1/healthz"
error="Get \"https://longhorn-conversion-webhook.longhorn-system.svc:9501/v1/healthz\": context deadline exceeded"
level=fatal msg="Error starting manager: conversion webhook service is not accessible after 1m0s sec"
```

**Cause:**
- Worker node's longhorn-manager cannot reach webhook service on master node
- Circular dependency: manager needs webhook, webhook needs manager to be ready
- DNS resolution failing intermittently
- CNI (Canal) may have MTU detection issues

**Solution Attempted:**
- Deleted and restarted pods multiple times
- Verified service endpoints exist
- Tested connectivity with curl test pods
- Restarted CoreDNS

**Result:** Master node's longhorn-manager runs, but worker node's manager crashes

#### Issue 4: longhorn-driver-deployer Stuck in Init

**Symptom:**
```
longhorn-driver-deployer-559d7fbbdd-mm8sb   0/1     Init:0/1   0             67s
```

**Cause:**
- Init container `wait-longhorn-manager` waiting for condition that never completes
- Circular dependency: deployer waits for all managers ready, worker manager can't start
- CSI provisioner never deployed, so PVCs remain Pending

**Result:** PVC stuck in `Pending` state, no CSI pods created

### Root Cause Analysis

**Primary Issues:**

1. **Resource Constraints:**
   - t2.medium (2 vCPU, 4GB RAM) is minimal for RKE2 + Longhorn
   - 8GB disk insufficient for Longhorn storage
   - Recommended minimum: t3.large (2 vCPU, 8GB RAM) with 50GB+ disk

2. **DNS/CNI Issues:**
   - RKE2's CoreDNS uses non-standard service name
   - Intermittent DNS resolution across pods
   - Canal CNI MTU auto-detection warnings
   - Possible network policy blocking inter-pod communication

3. **Architecture Mismatch:**
   - Longhorn designed for production with dedicated storage nodes
   - Single-node lab with minimal resources not ideal for distributed storage
   - Need proper infrastructure planning for Longhorn deployment

### Lessons Learned

1. **Infrastructure Requirements:**
   - Minimum 2 CPU, 8GB RAM per node for Longhorn
   - Dedicated storage volumes (EBS) recommended over root volumes
   - Minimum 50GB disk space per node for meaningful storage

2. **Pre-installation Checks:**
   - Verify DNS resolution works 100% before installing Longhorn
   - Test inter-pod connectivity across nodes
   - Ensure all nodes can reach all services
   - Check CNI MTU settings match network infrastructure

3. **RKE2 Specific Considerations:**
   - Create `kube-dns` service alias for compatibility
   - Check Canal CNI logs for MTU issues
   - Verify network policies don't block Longhorn traffic

4. **Alternative Storage Options:**
   - Use `local-path` for development and testing
   - Use EBS CSI driver for AWS production
   - Consider Rook-Ceph as alternative distributed storage
   - Evaluate storage needs before choosing solution

## Troubleshooting Guide

### Issue: Worker node not joining

**Symptoms:**
- `Failed to validate connection to cluster` errors
- Worker shows `NotReady` status
- Timeouts when connecting to master

**Solutions:**

```bash
# 1. Check connectivity from worker to master
ping -c 3 172.31.0.169
nc -zv 172.31.0.169 9345

# 2. Verify RKE2 agent is installed
dpkg -l | grep rke2

# 3. Check if security groups allow required ports
# Master needs: 9345 (RKE2), 6443 (API), 2379-2380 (etcd)

# 4. Verify token is correct
cat /etc/rancher/rke2/config.yaml

# 5. Check agent logs
sudo journalctl -u rke2-agent -n 50

# 6. Restart agent if needed
sudo systemctl restart rke2-agent
```

### Issue: Ingress not working

```bash
# Check ingress controller pod
kubectl get pods -n kube-system -l app.kubernetes.io/component=controller

# Check ingress controller logs
kubectl logs -n kube-system -l app.kubernetes.io/component=controller --tail=50

# Check ingress resource
kubectl describe ingress -A

# Check service endpoints
kubectl get endpoints -A | grep frontend
```

### Issue: Pod not starting

```bash
# Check pod status
kubectl get pods -n demo-app

# Describe pod for events
kubectl describe pod -n demo-app -l app=frontend

# Check pod logs
kubectl logs -n demo-app -l app=frontend

# Check node resources
kubectl describe node rke2-master-1
```

### Issue: Cannot access from browser

```bash
# Check AWS security group
# Make sure port 80 and 443 are allowed

# Check if nginx is listening
sudo ss -tlnp | grep nginx

# Check if firewall is blocking
sudo iptables -L -n | grep 80

# Test from inside first
curl -s http://localhost/demo/

# Then test from outside
curl -s http://13.58.33.90/demo/
```

### Issue: HostNetwork not working

```bash
# Verify hostNetwork is set
kubectl get daemonset rke2-ingress-nginx-controller -n kube-system -o yaml | grep -A2 hostNetwork

# Check pod is running
kubectl get pods -n kube-system -l app.kubernetes.io/component=controller

# Check nginx is binding to port 80
sudo ss -tlnp | grep :80

kubectl logs -n kube-system -l app.kubernetes.io/component=controller --tail=50
```
